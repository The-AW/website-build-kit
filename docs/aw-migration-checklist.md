# AW WordPress migration checklist

Use one copy per client in that site's repository, not in this public kit. See [aw-migration-process.md](aw-migration-process.md) for pinned scaffolding and exact commands. Keep each client site isolated; no CMS, Brevo, or imported client assets/secrets in the kit.

## Intake and source inventory

- [ ] Create the site repository and keep its own `CLAUDE.md` with durable decisions, target IDs and domain context.
- [ ] Fill `aw-migration.json`: WordPress source URL; production/staging hosts; repository and per-environment Cloudflare account, zone and Worker targets; route/media inventory paths; redirect exceptions; forms choice; acceptance and rollback.
- [ ] Fetch `robots.txt` and every sitemap index/child; record sitemap filenames and `Sitemap:` targets.
- [ ] Crawl navigation, page links, pagination, feeds, search, taxonomy, downloads, verification files and archives. Use a browser for JS-rendered routes; record console/network failures.
- [ ] Record each source URL, status, final path, canonical, title, description, language, indexability, page family and disposition. Preserve paths, metadata, structured data and the original language unless an exception is recorded.
- [ ] Capture desktop/mobile screenshots while the source is available; sample every page family.
- [ ] Inventory forms/integrations, destinations, account owners and actual data flow. Record email/DNS state read-only (MX, SPF, DKIM, DMARC and verification records); do not change mail flow as part of this migration.
- [ ] Create `recon/media.csv` with `source_url,local_path,status,sha256,alt,usage` and one row per source asset (or an explicit no-media row); record inaccessible assets and broken source links as gaps.

## Build and route parity

- [ ] Keep content and media in version-controlled files in the site repo. Reuse useful recon, extraction, media, URL, redirect, accessibility and verification checks.
- [ ] Map every source URL to a page, reviewed redirect/status, or explicit disposition; no catch-all to the homepage. Record redirect exceptions and test for loops and duplicate sources.
- [ ] Confirm the project is content-first and static-compatible; put dynamic routes only in explicitly enabled modules.
- [ ] Static is the default: no runtime adapter, form endpoint, Turnstile key, KV binding, or notification service. Optional modules do not block static migration.
- [ ] Set `forms.choice` explicitly to `none`, `d1_leads` or `private_crm`. Use `d1_leads` (leads in The-AW's shared lead database, one row per lead with this site's `site`; no CRM, no shared secret) when no CRM is required; `private_crm` only when the existing CRM is wanted. For `private_crm`, use same-origin `POST /api/leads` + Turnstile Siteverify + a site-specific adapter to AW's existing private CRM; ordinary pages remain prerendered and only API routes are on-demand. No email/Slack/Brevo notification transport is mandatory.
- [ ] The retained contact code is still a KV-only implementation draft, not the CRM integration and not proven end-to-end. Do not enable or claim it works unchanged; require an implemented adapter, request limits, recovery/privacy behavior and staging tests first.
- [ ] For `d1_leads`: bind the two SHARED lead databases (`websites-contact-crm-staging` / `websites-contact-crm-production`; never create a database or apply a schema for a site), use the site group's shared Turnstile widget (`aw-loans` / `aw-affiliate` / `aw-other`, its root domain added to the widget, same sitekey for staging and production), a unique rate-limiter `namespace_id`, and the two Worker secrets (`TURNSTILE_SECRET_KEY`, `LEADS_RATE_LIMIT_HMAC_SECRET`) set outside the repo. Submit the staging form in a real browser, confirm the row with `npm run leads:staging -- --reveal`, delete the synthetic row, then record `forms.productionAcceptance` before setting `forms.productionEnabled`; production stays closed until then. A rejected bad request (foreign Origin, non-JSON, oversize, bad token) must store nothing. Retention is the CRM's job (730 days); the contract is github.com/The-AW/websites-contact-crm `docs/site-contract.md`.
- [ ] For `private_crm`, verify API Worker-first routing, static page prerendering, staging noindex, production sitemap/robots/canonicals and a real static 404. A synthetic local adapter proves routing only, not hosted CRM delivery or browser form success.
- [ ] Migrated media follows `skills/website-build/references/build.md` §5b: deploy only uploads that pages use; one WebP per legacy raster sized ~2× its measured rendered width (cap 1600px); every reference rewritten and the build failing on a missing one; old `.png`/`.jpg`/`-WxH` URLs and attachment pages 301 in one hop through static `_redirects` rules (`scripts/legacy-redirects.mjs`, ≤2,000; no Worker runs for an old URL or a 404); `/wp-content/uploads/*` cached immutable for a year. Never deploy the original uploads byte-for-byte as the served images. The template ships the tools behind `media.legacyUploads: true` (off by default): `npm run legacy:stage`, `legacy:widths`, `legacy:webp`, `legacy:link`, `legacy:rewrite` (run by `npm run build:staging`), plus `npm run check:legacy-media` and `npm run test:legacy-media`. With it on, `not_found_handling` is `none` and an unknown URL must still return a real 404.
- [ ] Count deployed files against the Cloudflare plan cap (Workers Free: 20,000 per version, 25 MiB per file) before the first deploy with `npm run check:file-count` (the build and `deploy-aw` run it too), and record the count. Do not move to Workers Paid or R2 to fit unused media; back the unused media up outside the deploy instead.
- [ ] Reconcile redirects, sitemap paths, robots directives, feeds, verification files, `ads.txt`, `.well-known`, title/description/canonical/language/schema and indexability.

## Minimum launch — blocking

- [ ] Fresh staging and production builds use the host and distinct Worker target from the manifest; placeholder values, staging/production mixing and shared Worker names refuse.
- [ ] Every inventoried source URL resolves, redirects to a reviewed destination, or has a recorded disposition. Route families, internal links, local media, alt text, downloads and real 404 status pass.
- [ ] Staging is noindex and emits no production sitemap. Production canonicals, robots and sitemap use the verified production host.
- [ ] Performance measured on the deployed staging site with PageSpeed Insights for the home page and one page per family: LCP < 1.0s desktop, < 2.5s mobile, CLS < 0.1; used-media bytes before/after and no deployed raster over 200 KB without a recorded reason.
- [ ] Run accessibility, keyboard/focus, contrast and reflow checks; review representative desktop/mobile screenshots and browser console/network failures.
- [ ] Record site acceptance criteria, who/when, a rollback snapshot, WordPress origin and restore steps in the site repo/manifest. Preserve the WordPress origin through the recovery window.
- [ ] If forms are `none`, no form delivery, CRM, Turnstile or notification provider is a launch blocker. If forms are `d1_leads` or `private_crm`, test the full enabled path without sending unapproved real personal data.
- [ ] Keep DNS/mail unchanged unless included in the already-authorized scope. Do not ask again for authorization already granted in this session; do not widen scope implicitly.
- [ ] Cut over with a Worker **route** over the existing proxied record (`attach: "route"`, DNS unchanged, rollback = delete the route), following [production-cutover.md](production-cutover.md): prestate readback, the five-minute smoke test, rollback steps written before the window. A custom domain replaces the DNS record and makes rollback a DNS recreation with an NXDOMAIN gap.
- [ ] **Production equals `origin/<default branch>`.** The release PR is merged and pushed, and production was deployed from a clean checkout of the default branch (`npm run deploy:production` refuses anything else). The live Worker version's tag is a commit on `origin/<default>` (`npx wrangler versions list --name <worker>`), and no `--allow-unmerged` record in `BUILD-STATE.md` is still open. "Deployed from a branch, PR open" is not a go-live.
- [ ] `http://` on the production host 301s to `https://` with the path and query preserved. A Worker route does not do this by itself (the old origin did, so nobody checks); `npm run verify -- https://<production-host>` fails without it. Add it as one Single Redirect rule, not as a zone-wide setting.
- [ ] **Inventory every other domain that points at the old server** (old brand names, typo and vanity domains, on the same Cloudways/shared host) before it is retired, and decide each: 301 to the new site, keep, or lapse. Do the 301s at the edge with Single Redirect rules, following [sops/301-redirects-the-aw](https://github.com/The-AW/seo-sops/tree/HEAD/sops/301-redirects-the-aw) in The-AW/seo-sops (its Cloudflare token permissions table lists the rights to create them). Leave MX/TXT alone. Record each domain, zone, ruleset ID, old records and rollback.
- [ ] Affiliate / product-roundup sites: both money-page gates pass on **deployed** staging and again on production: `npm run lcp` (observed median LCP ≤ 500 ms and CLS < 0.1 at 1440 and 390 px) and `npm run check:money` (every outbound affiliate link, price table and text identical to the old site; every link visible and clickable; images loaded). Any conversion difference is a stop. See `skills/website-build/references/archetypes.md` §Affiliate roundups.
- [ ] CI for a site whose media is kept outside Git: the gates workflow runs `node scripts/media-available.mjs` and builds with `AW_ALLOW_MISSING_MEDIA` set when the originals are absent, so the media steps are skipped with a notice instead of failing every push. That build is marked undeployable; the production build ignores the switch and fails. Run the full build where the media is before any deploy.
- [ ] Do not retire Cloudways at cutover. Before any later retirement, verify a backup and check shared-server dependencies; other sites may still use that server.

## After launch — polish, tracked separately

- [ ] Monitor redirects, 404s, indexing, selected analytics and any enabled CRM path.
- [ ] Track copy, imagery, visual refinement and non-essential integrations as post-launch work, not static-release blockers.
- [ ] Keep the WordPress origin and rollback material until the owner confirms the recovery window has passed.
