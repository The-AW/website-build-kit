# AW website migration process

This is AW's reusable process for moving an existing marketing or content site into a site-specific repository. It is a process guide, not a client specification. Record client URLs, content, screenshots, credentials, analytics identifiers and form submissions only in that client's repository or approved private systems; never in this public kit.

## Baseline decisions

- **Keep repositories separate.** The kit contains reusable methods and a generic starter. Every site gets its own repository, deployment configuration, content, assets, secrets and persistent `CLAUDE.md` context. A kit change does not update a site already scaffolded from it; make site-specific changes in the site repository, not by copying client files into this kit.
- **PagesCMS is the selected AW CMS default for owner-editable content.** PagesCMS edits files in the site's GitHub repository through a site-specific `.pages.yml`; it has no separate content database. Map the audited content/media fields and test a save before handover, because fields absent from the CMS schema can be lost when a file is rewritten. The generic starter does not ship `.pages.yml`, so configure and validate it per site. A no-CMS exception is appropriate only when there is no ongoing editorial editing need and that decision is recorded. Cloudflare EmDash remains a future evaluation only, not a current dependency. [PagesCMS documentation](https://pagescms.org/docs/)
- **Use Astro with Cloudflare when the site fits, and separate static hosting from runtime.** A purely static Astro build can deploy `dist/` as Workers Static Assets with Wrangler; it needs no Astro adapter, application Worker script, or runtime bindings. On-demand routes, server rendering, or Cloudflare bindings require a Worker runtime; use the supported Astro Cloudflare adapter for those Astro features. The current kit template is not static-only: it has static pages plus a non-prerendered contact API route and KV/email bindings. Choose a different stack when the site is an application, needs unsuitable runtime behavior, or has an existing platform that should remain. Re-check the official guides and lockfile for each project. [Astro Cloudflare integration](https://docs.astro.build/en/guides/integrations-guide/cloudflare/) · [Cloudflare Workers Astro guide](https://developers.cloudflare.com/workers/framework-guides/web-apps/astro/)
- **Own the contact-form path and bot protection.** Do not preserve or re-embed LeadConnector. Use the source-controlled same-origin endpoint and Cloudflare Turnstile; the generic template now renders the widget and validates each non-honeypot submission through Siteverify, checking token success, hostname and `contact` action. Set the public `PUBLIC_TURNSTILE_SITE_KEY` in the build environment and `TURNSTILE_SECRET_KEY` as a Worker secret. Rate limiting, an overall body-size cap, duplicate/idempotency handling, Slack delivery and durable notification recovery remain site-project work. [Turnstile client widget](https://developers.cloudflare.com/turnstile/get-started/client-side-rendering/) · [Server-side validation](https://developers.cloudflare.com/turnstile/get-started/server-side-validation/)
- **Treat deployment and DNS as separate approvals.** A migration may prepare a build and a cutover plan, but must not publish, change production DNS, or alter MX/email records unless those actions are separately authorized.

## Migration stages and gates

### 1. Reconnaissance before implementation

Capture a baseline while the source site is still available. Inventory URLs from `robots.txt`, every sitemap index and child sitemap, navigation, feeds, search results, archived routes and any platform export. For WordPress, inspect the REST API when available, but compare it with rendered pages; a database or API export alone may omit builder-rendered content. Use a real browser for JavaScript-rendered pages and for the visual baseline.

For every route, record the source URL, final path, page family, response status, canonical, title, description, language, indexability and intended disposition. Inventory redirects, pagination, taxonomy, image and download URLs, structured data, verification files, analytics, consent, booking, chat, search and all forms. Record email hosting and DNS records read-only. Mark inaccessible resources and make no silent substitutions.

**Gate:** route inventory, integrations inventory, desktop/mobile screenshots and an owner-visible list of missing access or content exist before routes or designs are rewritten.

### 2. Extract content and media without changing meaning

Preserve the source language, route slugs, headings, body copy, image alt text, internal links, metadata and structured data unless an owner-approved change is recorded. Use rendered HTML as the visual/content reference; use CMS exports or APIs as additional sources, not as proof that every rendered page was captured. Store content in files with a documented schema and preserve one source of truth.

Keep media in the site repository where appropriate. Create a manifest with the original URL, local path, fetch status, hash, alt text and any usage/licensing note. Keep source originals apart from generated responsive formats. A failed or blocked image is a review item, not permission to invent a replacement. Verify that every intended local media reference resolves after the build.

**Gate:** route-to-content mapping and media manifest have no unexplained gaps; every exception has an owner decision or an explicit open item.

### 3. Create the site-specific project

Scaffold from the kit only after recon establishes that its architecture fits. Keep the site in a separate repository. Update that repository's README and `CLAUDE.md` with the chosen stack, route and content conventions, service accounts, form behavior, privacy/retention assumptions and deployment boundaries. Never copy project material, tokens or account IDs into this kit.

Keep content in versioned files in the site's GitHub repository. For owner-editable content, configure PagesCMS after the content inventory and map the actual fields in a site-specific `.pages.yml`; do not apply an unvalidated generic schema. Record a no-CMS exception only if there is no ongoing editorial editing need. EmDash may be assessed later if requested; evaluate its current maturity, editorial workflow, hosting and migration/export behavior at that time rather than assuming it is available or suitable now.

### 4. Implement routes, content and integrations

Build reusable components around the source site's page families without imposing the kit's sample design on the migrated site. Keep canonical URLs, sitemap behavior and redirects tied to the route inventory. Do not redirect an old route to the homepage as a catch-all. Keep structured data truthful and based on verified business facts.

Replace third-party forms as a distinct integration task. A form's visual embed is not the same as its lead-capture, CRM, notification or autoresponder behavior. Document which capabilities are intentionally retained, replaced or dropped. If a third-party account is unavailable or prohibited, do not silently leave its script or iframe in production.

### 5. Contact form and email architecture

The recommended AW baseline is a **first-party, source-controlled endpoint** in the site's repository. Use a Worker runtime when the endpoint is implemented on Workers; a purely static Astro build has no server route or bindings:

1. The browser submits a native HTML form to a same-origin route such as `/api/contact/`. Match Astro's configured trailing-slash behavior and test that the POST reaches the handler directly; a redirect after POST can lose the submission.
2. Allow only the intended content types and fields, cap the total request-body size before parsing, and validate field types, lengths and required values. Check `Origin` when present as defense in depth, then apply a honeypot and rate limiting. Include Turnstile in the AW baseline and call Siteverify on the server for each submitted token. Reject missing, invalid, expired or replayed tokens and handle Siteverify outages with a recoverable error; never bypass verification silently. Turnstile's client widget alone does not protect the endpoint.
3. If the owner wants a submission archive, persist the minimum necessary fields before notifications. Set retention and deletion rules for each store, avoid personal data in logs and storage metadata, and secure any export route. KV expiry does not expire copies in an inbox, Slack workspace, provider logs or backups. If no archive is required, do not retain submissions merely because the code can.
4. Use Brevo as the AW default email notification provider. Verify a sender on the site's domain, keep `BREVO_API_KEY` in the Worker secret store, separate staging recipients, and put the visitor's address in `Reply-To`, never `From`. Slack may be added as an explicitly approved additional or alternative channel; its webhook URL is a secret tied to the selected channel, and messages cannot be deleted through Incoming Webhooks. Send only the minimum needed in Slack and account for workspace retention. See [Slack's Incoming Webhooks documentation](https://api.slack.com/messaging/webhooks).
5. Define partial success and recovery. If the archive accepts a lead but a notification fails, do not tell the visitor to resubmit; alert an operator or queue a retry. Test each channel independently and keep staging destinations separate. A notification acknowledgment does not prove that a person read or acted on the lead.

This is the recommended open-source/self-controlled approach: the MIT-licensed kit's first-party handler runs in the site owner's Worker account and is copied into that site's separate repository. It removes the LeadConnector form/CRM dependency and keeps validation, form behavior, storage choices and tests in the site's own source. The current reference is [`template/src/pages/api/contact.ts`](../template/src/pages/api/contact.ts), with validation in [`template/src/lib/lead.ts`](../template/src/lib/lead.ts) and notification in [`template/src/lib/brevo.ts`](../template/src/lib/brevo.ts).

Reuse the handler as a pattern, not an unchecked drop-in: the current route supports Turnstile/Siteverify, but has no overall request-body size cap, request rate limiting, duplicate/idempotency protection, Slack adapter, durable notification retry or alert for delivery failure. When KV succeeds but Brevo fails, the current route still returns success to the visitor and only writes an error to Worker logs; no automatic retry is implemented. A client retry can create another lead and notification. Its lead record stores IP, user-agent and country, while the Brevo message sends the visitor's name, email, phone, service, page and free-text message. Remove fields not needed for an explicit purpose and include every processor and copy in privacy, access, retention and deletion decisions. Brevo is the selected AW default and current template adapter. For a simple append-only archive, KV with TTL may be sufficient; choose D1 only when queryable/admin workflows are documented requirements. Neither is a CRM.

**Cloudflare Email Routing and Email Sending are different capabilities.** Email Routing handles *incoming* mail for a domain and can forward it to a verified destination or process it with a Worker; it is not a mailbox or an outbound form-notification sender. It requires Cloudflare DNS and changes root-domain MX records; it cannot be layered over another provider's root MX records without a planned mail cutover. Use it only after reviewing the existing mail flow and obtaining separate owner approval. [Email Routing setup](https://developers.cloudflare.com/email-service/get-started/route-emails/)

Cloudflare Email Service **Email Sending** is a researched alternative, not the selected AW notification default. As of 2026-11-06, Cloudflare's official overview labels it **Beta**, and Cloudflare announced public beta on 2026-04-16. A Worker can use the native `send_email` binding. Before a sending domain is onboarded, recipients are limited to verified account destination addresses; sending to arbitrary recipients requires Workers Paid and an onboarded sending domain. The current pricing page lists 3,000 outbound emails included per account per month on Workers Paid and $0.35 per additional 1,000; new accounts also start with conservative daily limits that can change with sending behavior. Sending-domain onboarding adds bounce/authentication records under `cf-bounce` plus a DMARC record at the root; these differ from Email Routing's root MX records. Review existing SPF and DMARC records before onboarding—do not replace or duplicate them blindly. Consider Email Sending only after an explicit owner decision to depart from Brevo and acceptance of beta status, plan eligibility, quota and deliverability risk. Do not change DNS as part of this process. [Email Service overview](https://developers.cloudflare.com/email-service/) · [Workers send API](https://developers.cloudflare.com/email-service/api/send-emails/workers-api/) · [Email Sending limits](https://developers.cloudflare.com/email-service/platform/limits/) · [Email Service pricing](https://developers.cloudflare.com/email-service/platform/pricing/) · [Domain configuration](https://developers.cloudflare.com/email-service/configuration/domains/) · [Public beta announcement](https://blog.cloudflare.com/email-for-agents/)

If beta email is not acceptable, use a mail provider explicitly chosen by the owner, or separately scope a self-hosted open-source mail transfer service. Self-hosting mail brings ongoing responsibility for queues, bounce handling, reputation, SPF/DKIM/DMARC, abuse controls and deliverability; do not make it the default for a low-volume contact form without an operator who will own it.

### 6. Verify parity and behavior

Use the complete source URL inventory as the expected set. Build and type-check the site, then compare built and served routes with the old inventory. Test internal links, redirects, sitemap and robots behavior, canonical and metadata parity, structured data, local assets, real 404 status, console/network failures, accessibility and representative desktop/mobile layouts. Check each page family, not only the homepage.

Exercise the contact route with valid, invalid, malformed, cross-origin, empty, duplicate and honeypot submissions. Verify rate limiting and Turnstile Siteverify behavior, including missing, expired, replayed and invalid tokens plus Siteverify outage. Confirm storage, email and Slack separately, including provider failure, duplicate retry behavior, retention, export authorization and the visitor-facing success/failure state. Never send real email or post personal data to a production Slack channel during tests; use approved staging destinations.

**Gate:** automated checks pass and visual differences are reviewed. The form must have server-side Turnstile validation, a rate-limit control, a tested recovery path for every enabled notification channel, and privacy/retention rules covering the archive and notification copies. Any exception needs a named owner decision and written risk acceptance; unresolved security, privacy or delivery failures block launch readiness.

### 7. Handover and rollout planning

Deliver the source repository, content/media manifests, route and redirect inventory, test evidence, service/binding list, secrets setup instructions, contact-form data-flow description, retention and deletion policy for the archive and each notification copy, rollback instructions and open decisions. Capture DNS and email records read-only before any cutover. Check MX, SPF, DKIM, DMARC and verification records independently from website records.

Deployment, production cutover, DNS changes and changes to existing email routing are not implied by a successful build. They require a separate, explicit owner-approved rollout step with a tested rollback and monitoring plan. During the first week after an authorized launch, check 404s, form submissions, delivery failures, analytics continuity and Search Console coverage.
